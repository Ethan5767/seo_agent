## 1. The provenance gate was porous to exactly what it exists to stop (B-034 — fixed)

**What happened.** `claim_provenance_check` is the gate CLAUDE.md describes as
the answer to "the error class models produce most fluently" — an invented
rating, review count or year-count in copy the agent rewrote. Its numeric half
was close to inert, for two independent reasons.

**(a) A work item's `evidence` contributed its numerals to the corpus.** Evidence
is a measurement *of the page*: `len=106`, `words=478`, `count=12`. Doctrine
admits it as a source and is right to — it is real. But it is never a fact
*about the business*, and flattened into one corpus it sourced any claim that
happened to share a digit string. On lee's 2026-08 cycle that is 190 evidence
strings carrying 38 distinct integers, 25 of them below 200.

**(b) A claim with a dedicated config home was matched against the whole config.**
`option_full_threshold_pages: 10` — an architectural escalation threshold —
sourced *"Trusted for over 10 years"* for a client whose `years_in_business` is
blank.

**How bad.** Against the real client, with the gate as shipped at v3.0.0, a diff
adding `"106% more hydration, 478 customers served, from $12."` to
`lib/constants.ts` produced:

```
[OK] claim-provenance: every claim in 1 changed file(s) resolves to a source.
exit=0
```

Not one of those three numbers is a fact about that business. After the fix:
3 unsourced, exit 18.

**The fix.** Evidence contributes its **words but not its numerals** (digits
substituted to `#`, not deleted, so `len=106` cannot collapse to `len=` and abut
the next token's digits). `rating`/`reviews`/`years`/`license` resolve against
`trust_signals.rating`/`.reviews`/`.years_in_business`/`.licenses` **alone**; a
blank, zero, empty-list or `<x.x>` placeholder field sources nothing, which is
the point.

**What is deliberately not scoped.** `warranty` is the fifth kind CLAUDE.md names
as legal exposure and has **no config field anywhere in the schema**. Scoping it
to a key that does not exist would refuse every warranty term unconditionally —
a product decision, and a human's. It stays on the general corpus.

**Narrowed, not disarmed.** A client who has declared `years_in_business: 28`
still resolves 28, and 30 is still refused. The prior version of a file is still
checked *without* the scope, because a claim already published was not invented
by this diff and refusing inherited copy on every reflow is how a gate gets
switched off.

## 2. `audit_ssr` was red on five things that cannot run at server render (B-036 — fixed)

**This is B-027's lesson from the other side, and it is the one worth
internalising.** B-027 (shipped in v3.1.0) fixed where this gate *looks* — it
used to search only `src/`, which `create-next-app` does not create by default,
so the common Next layout got a silent green from a never-baselineable gate.

Pointed at a real client for the first time, it reported `[FAIL] 4 files have
SSR-dangerous patterns`. Six violations. **Five were false positives.**

**(a) The early-return guard had never matched anything.** `_mask` blanks string
contents before anything is scanned:

```
raw   :   if (typeof window === "undefined") return Promise.resolve();
masked:   if (typeof window ===            ) return Promise.resolve();
```

`EARLY_RETURN_GUARD` requires the quoted `'undefined'` literal that masking just
deleted. The module docstring has documented early-return guards as an SSR-SAFE
case the whole time. Four of the six findings sat inside functions whose **first
line** was that guard.

**(b) A multi-line function signature opened no function frame.**

```tsx
export default function AddressPanels({   // no closing paren on this line
  addresses,
}: Props) {                               // no `function` on this line
```

Neither line is recognisable alone, and that is how **every React component with
named props is written**. The lost frame undercounts depth for the whole file, so
`window.confirm` inside a click handler read as a render body.

**The general rule.** CLAUDE.md sharp edge #4 already says a gate that scanned
nothing must never report a pass. This is the mirror: **a never-baselineable gate
that over-reports makes a PR permanently red for no defect, and both ends with
the gate switched off.** When you add a gate, decide what its empty input means
*and* what its noise floor is.

**The surviving finding is the documented ceiling.** The depth-1 rule cannot tell
a plain exported helper from a component render body without real parsing, so
`function navigateAfterAuth() { window.location.assign(…) }` is still flagged. I
fixed that one in lee's source rather than in the gate — a browser-only helper
should carry its own guard, and a no-op during server render is correct
behaviour rather than a throw. Method-shorthand signatures spread over lines
(`async handleX(` with no `function` keyword) remain unrecognised; the failure is
toward over-reporting, which is the safe direction here.

## 3. The render-source path, and two things that would have made it lie (B-037, B-038, B-039 — fixed)

`render_url` is the supported answer to sharp edge #4 for a client with no static
export: `wf-render-snapshot` crawls a rendered deployment into the tree the nine
OUT gates already glob. It had never been used. Three defects sat between it and
a correct verdict, and they were found in the order you would find them.

### B-037 — an auth wall crawls perfectly

`curl` and `curl_status` both follow redirects. That is deliberate and correct: a
site with a no-trailing-slash policy needs it. **An auth wall exploits exactly
that.** Vercel Deployment Protection answers *every* route with a 302 to
`vercel.com/sso-api` and a 200 login page; Cloudflare Access and Netlify password
protection do the same to their own domains.

So every route returns 200, every body is real HTML, and the crawler's only
refusal — *"no page was fetched"* — never fires. It would have written 26 copies
of a login screen and every OUT gate would have judged that as the client's site.

**Sharp edge #4's dangerous case is green over nothing. This is green over the
wrong thing, and it is worse** — a full, plausible `./out` with no empty
directory to notice.

New `common.curl_final_host()` reports the host a URL actually lands on.
`snapshot()` probes the first route **before writing anything** and refuses at
exit 19 when it lands off-host. Compared by host, not URL, so a same-host
redirect is untouched; an unreachable host still gets the empty-crawl message
rather than being called a wall.

Proven against the real walled preview — `[REFUSED]`, and no output directory
created.

### B-038 — the blocking list asked the wrong question

The OUT gates were correctly rewired to key on `steps.tree.outputs.ready`, so a
crawled tree is judged like a built one. The **blocking** list was not:
`[ "$BUILD" = "failure" ]` reads `steps.build.outcome` directly.

A client with no static export fails its build **on purpose** — `./out` is never
produced, which is the documented safe state — and supplies `render_url` so the
crawl provides the tree. That client would run all nine OUT gates against the
crawled tree, pass every one, and still be reported RED on BUILD, while the
summary table twenty lines above printed `| BUILD | **crawled** <url> -> ./out |
19 | ✅ |` **in the same sticky comment**.

### B-039 — and then the fix for it did not work

**This is the one to remember.** The evaluate step has **two** lists over the same
gate names. `add_fail` builds the sticky PR comment; a separate
`for g in TSC SSR … BUILD … ACCEPTANCE` loop reads `"${!g}"`, emits the
`::error::` annotation, sets `red=1` and exits 1. **Only the loop decides.**

B-038 rewired the comment and left the loop. v3.1.2 shipped. The real client
caught it one release later — run **31471589695**, pinned to the freshly cut
`@v3.1.2`, still annotated `Blocking gate failed: BUILD`.

The test I had written did not catch it because the loop reads the variable
**indirectly**. The literal string `[ "$BUILD" = "failure" ]` really was gone,
which is exactly what the assertion checked, so **it passed over a broken
workflow**.

> This is CLAUDE.md §4's *implemented is not wired* (B-007) one layer further in.
> The call site is a bash word inside a loop list. No unit test of any Python
> module can reach it, and the obvious text assertion matched the half that
> decides nothing.

The replacement test **parses the loop's gate list** rather than grepping,
asserts `BUILD` is absent from it, and asserts six gates that must remain present
so it cannot be satisfied by emptying the loop. Confirmed to bite by re-inserting
`BUILD`.

## 4. lee's legal gates are both off (B-035 — OPEN, needs the client)

`docs/client-config.yml` declares `forbidden_phrases: []`. That is the
three-state contract's explicit "this client has no banned phrases" decision, and
**the engine is behaving exactly as designed** — both gates SKIP and both say so
rather than reporting green:

```
[SKIP] no ruleset to self-test … a recorded human decision, not a ruleset that passed.
[SKIP] source mode not run … This is a recorded human decision, not a clean sweep.
```

The problem is the reasoning behind it. The comment under the declaration reads
*"The default no-dollar-amounts rule does NOT apply here: leeserie.com is a
storefront and prices are the product."* That is a sound argument for dropping
`\$[0-9]`. It is not an argument that the client has **no** banned phrases — but
an empty list is all-or-nothing, so one rule's removal took the whole ruleset
with it.

**Why it is worth a row rather than a shrug.** `forbidden_sweep` is
never-baselineable *specifically for legal exposure*, and lee sells cosmetics
including pregnancy and stretch-mark products, which is the category where the
cosmetic/drug claim line is regulated. The live copy already sits on it:

- `lib/seo-constants.ts:11` — *"built to help you **heal** … your skin"*
- `lib/page-meta.ts:18` — the same *"heal"*
- `lib/learn-guides.ts:27` — *"cleanse, **treat**, and seal in one routine"*

`heal` and `treat` are the two verbs that distinguish a cosmetic from a drug
claim.

**I did not fix this and will not.** Writing a legal ruleset for a paying
client's live site is derivation from something I do not have: their regulatory
position, their market (Cambodia, not FDA jurisdiction by default), and whatever
counsel they have taken. Inventing one is the exact failure
`claim_provenance_check` exists to prevent, applied to the ruleset instead of the
copy.

**The ask:** the operator asks the client, then either declares real rules or
re-affirms the empty list on its own merits rather than on the price-rule
argument. Files alongside **B-008** — both are "the legal-adjacent gates have no
partial state".

Two smaller engine questions this raises, both open rather than
recommendations: (1) should `bootstrap_config` refuse to write
`forbidden_phrases: []` in the same edit that deletes the default rule, since the
two decisions got conflated here; (2) should the skip message name the client's
declared sector.

first client onboarded without the secret settles it. The checklist says the same

## 6. The tier gate refused my own commit, and was right to

Worth knowing before it happens to you. I put the caller bump
(`.github/workflows/quality-gate.yml` + `seo-health.yml`) on the cycle branch,
and the gate refused it:

```
[REFUSED] .github/workflows/quality-gate.yml: on the deny list — refused at every tier, T3 included
[REFUSED] .github/workflows/seo-health.yml:   same
[BLOCKED] 2 of 12 changed path(s) exceed T3
```

`.github/**` is on `DEFAULT_DENY` at every tier because the agent must never edit
the gates that judge it — and **the gate judges the PR diff, so it cannot tell an
operator's commit on a cycle branch from the agent's.** That is the model working,
not a false positive.

**CI caller changes go on the client's `main`, as a human commit.** Then merge
`main` into the cycle branch and they leave the PR diff. Same for the
`navigateAfterAuth` guard in §2 — it keeps the cycle PR purely the agent's work,
which is what `changelog.json` and `acceptance_check` are about.
