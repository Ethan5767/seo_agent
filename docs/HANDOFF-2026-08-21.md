### 2a. What `wf-site-health` does

13 built-in HTML checks (title/desc length, h1 count, canonical, noindex,
og:image, schema type + BreadcrumbList, forbidden phrases, phone/tel link,
GA4 tag, alt text, thin content) — always on, no credentials, pure
HTTP+regex. Any check whose config input is unset is skipped and **named on
stderr**, never silently passed as clean.

Then four optional enrichments, each its own CLI flag
(`--with-crux`/`--with-gsc`/`--with-dataforseo`/`--with-serp`), each needing
its own credential, off by default:

| Enrichment | Credential | Who it depends on |
|---|---|---|
| CrUX (`crux_findings`) | `CRUX_API_KEY` | **pipeline-side** — operator's Google Cloud key |
| DataForSEO On-Page (`dataforseo_findings`) | `DATAFORSEO_LOGIN`/`PASSWORD` | **pipeline-side** — operator's paid account |
| Bright Data SERP (`serp_findings`) | `BRIGHTDATA_API_KEY`/`BRIGHTDATA_SERP_ZONE` | **pipeline-side** — operator's paid account |
| Google Search Console (`gsc_findings`) | `GSC_ACCESS_TOKEN`/`GSC_SITE_URL` | **client-dependent** — needs that specific client's own property access |

This is the corrected categorization from the session (an earlier draft
lumped GSC in with the vendor APIs — wrong; GSC is the one enrichment that
literally cannot run without that specific client granting access, the
other three are a one-time operator setup cost that benefits every client).

Output: `docs/audit/<YYYY-MM>/findings.json`, with a `providers` block
recording each enrichment's status string (`ok:`/`partial:`/`skipped:`/
`failed:`) so "never asked" and "asked and found nothing" are always
distinguishable. Two guardrails worth knowing: refuses at exit 19 if every
URL was unreachable rather than writing an empty report; warns if one
finding code makes up ≥50% of a run (the B-009 false-positive smell test —
1,272 false findings from one broken regex, once, for real).

### 2b. CrUX has no fallback for a new/low-traffic site — OPEN GAP, not yet scoped as work

CrUX is real-Chrome-user field data. A brand-new site has ~0 recorded
navigations, so `crux_findings` returns `no field data: CrUX has no record
for <domain> (too little traffic)` and the cycle produces **zero** Core Web
Vitals findings — not wrong, just silent, forever, until the site earns
enough traffic.

Lighthouse (lab data, no traffic threshold, works day one) is the obvious
fallback and **already exists in this system** — but only inside
`preview.reusable.yml`, opt-in, Cloudflare-only, scoped to PR previews. It
is not wired into `wf-site-health`/`providers.py` as a general "CrUX empty →
run Lighthouse instead" path. Building that would be new work — an 8th
provider path, not a flip of an existing one. Nobody has scoped file-level
changes for this yet; it's a named gap, not a plan.

### 2c. Bright Data → DataForSEO SERP swap — SCOPED AS A PLAN, explicitly not implemented, then reverted once when tried

The operator wants to drop Bright Data as a vendor entirely and do
rank-checking through DataForSEO's own `serp/google/organic/live/advanced`
endpoint instead, reusing the `DATAFORSEO_LOGIN`/`PASSWORD` credentials
`dataforseo_findings` already needs — one fewer vendor, one fewer credential
pair for the whole system.

**Confirmed via DataForSEO's own docs this session** (not guessed):
`POST https://api.dataforseo.com/v3/serp/google/organic/live/advanced`,
body `[{"keyword", "location_code", "language_code", "device"}]`, response
`tasks[0].result[0].items[]` where organic results carry `type: "organic"`,
`rank_group` (organic-only position — the direct analogue of Bright Data's
old `rank` field), `rank_absolute` (position including ads/features — not
used, matches why the old code preferred `rank` over `global_rank`),
`domain`, `url`.
