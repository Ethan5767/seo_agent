## 1. Two agents, one checkout (B-012 — fixed)

**What happened.** Clicking RUN twice on the Runs screen started two
`wf-site-remediate` processes against the same repo. Both drive Claude Code with
Write/Edit over the same files; the loser's edits are overwritten with nothing
said, and `changelog.json` is written wholesale at the end of each run, so the
second finisher's copy is the only record that survives.

Observed on lee: runs at 08:40 and 08:58. The 08:40 one produced 706KB of agent
output and died without writing a changelog, leaving the previous day's
all-errored file in place. It looked, from the artifacts alone, like nothing had
happened.

**Fix.** `busy_run(slug)` in `pipeline/dashboard/server.py` returns the live run
for a client; `_launch` refuses a second one with HTTP 409. Check-and-insert
happen under `RUNS_LOCK` because `ThreadingHTTPServer` serves concurrent POSTs
and a bare check lets both callers through.

Keyed on **slug**, not cwd — onboard's cwd is the shared clients dir, so a cwd
key would make two unrelated onboards block each other while still permitting
the real conflict.

**Known scope, and it matters:** `RUNS` is per-process. This covers the console
and **not** a `./run.sh wf-site-remediate` typed in a terminal. Two operators on
two machines sharing a checkout are also uncovered. A lockfile in
`remediate.py` is the upgrade if either path bites.

Proof: `tests/test_dashboard.py::test_a_live_run_makes_that_client_busy`,
`::test_a_finished_run_does_not_block_the_next_one`,
`::test_another_clients_run_does_not_block`. Suite `419 passed in 2.65s`.

## 3. Capped runs do not resume (B-013 — open)

**The claim.** `remediate.py:40` states that on hitting `--max-items`, "the
remaining items keep their place in the worklist for the next run."
`CLAUDE.md` repeats it.

**The code.** `selectable()` rebuilds the queue from `worklist.json` sorted by
`(lane, id)` and never reads `changelog.json` (`remediate.py:308-317`). Run two
starts at item 1 and re-attempts the same first N. Meanwhile `main` writes
`changelog.json` wholesale (`remediate.py:442-443`), so run two's record
replaces run one's.

**Consequence.** The documented "run 10, then run 10 more" workflow silently
does the same 10 twice and clears the audit trail for the items that were
actually fixed. The only way through a worklist today is one run with the cap
raised.

**Three candidate resolutions, not equivalent:**

1. Make `selectable()` skip items already `status: "fixed"` in the cycle's
   changelog. ~4 lines, re-runs resume. But it changes what a re-run *means*,
   and `acceptance_check` is the component entitled to decide a fix held — not
   the model's own changelog entry.
2. Make `main` merge into an existing changelog rather than overwrite.
   Preserves the audit trail without touching queue semantics, but a re-run
   still redoes the work.
3. Correct the two docs to say "re-runs restart; raise the cap instead." Zero
   code, and honest.

My read: **3 now, 2 if multi-run cycles become normal.** 1 needs Alex's call
because it moves authority from the gate to the changelog.

## 4. The onboarding scaffold cannot be committed on a cycle branch (B-014 — open)

**What happened.** The documented dashboard sequence — branch → STAGE ALL
CHANGES → commit → push → PR — would have opened a PR that `tier_check` refuses
with exit 17.

`wf-scaffold-client-docs` writes five files and `wf-bootstrap-config` writes
`docs/client-config.yml`. On a T1 client every one is a **create**. Verified by
running `tier_verdict` over lee's real `git status -uall`:

```
OK      docs/audit/2026-08/{findings,worklist,report,changelog}.json   cycle artifact
REFUSED docs/client-config.yml       on the deny list — refused at every tier, T3 included
REFUSED docs/INDEX.md                create not permitted at T1
REFUSED docs/seo-progress.md         create not permitted at T1
REFUSED docs/seo-work-log.md         create not permitted at T1
REFUSED docs/cycle-logs/.gitkeep     create not permitted at T1
REFUSED docs/intake-archive/.gitkeep create not permitted at T1
```

The deny floor is right and must not be relaxed — it is what stops an agent
raising its own tier. The gap is that **no step in the pipeline ever commits
the scaffold**, so the operator meets it as a gate refusal rather than an
instruction.

**Workaround used on lee** (this is the missing documentation):

```bash
git checkout main
git add docs/INDEX.md docs/client-config.yml docs/seo-progress.md \
        docs/seo-work-log.md docs/cycle-logs docs/intake-archive
git commit -m "docs: onboard lee — client config and pipeline docs"
git push origin main
git checkout cycle/lee-2026-08 && git merge --ff-only main
```

The cycle PR then carries only `docs/audit/<cycle>/` plus the source files the
agent edited, all of which pass.

**Note this cannot be done in the dashboard.** Its only staging action is
`git add -A` — correct, per B-011 — which means selective staging needs a
terminal. If onboarding is meant to be a console-only flow, that is the thing to
fix.

Candidates in the ledger. The honest minimum is (c): print the exact `git add`
line at the end of `wf-onboard` and put it in `HOW-IT-WORKS.md`.

## 5. Local gates pass over nothing (B-015 — open)

`tier-check` and `claim-provenance` are offered on the Runs screen as pre-PR
checks, and the natural order is remediate → check → commit. Both gates diff
`origin/main...HEAD` — the **three-dot** form, comparing commits, blind to the
working tree.

So running them on a dirty checkout with no cycle commit yields an empty diff,
every check passes vacuously, and the console prints
`Clean — every check passed`.

That is precisely the failure the exit vocabulary exists to prevent: a run that
judged nothing rendering identically to a run that judged everything and
approved it.

**Operational rule until this is fixed: commit first, then gate.** Nothing in
the UI or the docs says so today.

## 5b. Provenance refuses every first PR (B-016 — open, blocking)

Found by actually running the gate on lee's real cycle commit, after B-015 had
been worked around by committing first.

```
[CORPUS] 148 words from: docs/client-config.yml, docs/audit/2026-08/worklist.json
[UNSOURCED] docs/audit/2026-08/report.md: 'first' (superlative) — 'first' appears
            in no config field, no work-item evidence, and not in the previous
            version of this file.
[BLOCKED] 1 unsourced claim(s).
exit 18
```

The offending text is `report.md` line 5:

```
- Compared Against: nothing — this is the first cycle
```

`wf-site-plan` wrote that (`plan.py:219`). `.md` is in `TEXT_SUFFIXES`, so the
gate scans every changed markdown file as human-facing prose — including the
audit report it generates itself. Meanwhile `tier_check` classifies the exact
same file as a `cycle artifact` and passes it. **The two gates disagree about
what `docs/audit/**` is.**

It reproduces on every client whose cycle has no prior to ratchet against — i.e.
every client's first PR, forever, until this is fixed.

**I did not work around it.** Relaxing a gate so your own PR goes green is the
move the deny floor exists to prevent, and it does not stop being that move
because the operator is a human rather than the agent. The PR is open and red,
which is the correct state.

Candidates are in the ledger; (a) skipping `docs/audit/**` in `prose_from` is
the real fix, since it puts the two gates back in agreement. Needs a call on
whether any part of `docs/**` should still be provenance-scanned.

## 6. Live instances of known sharp edges

**#4, static export — hit.** lee is `nextjs-16-app-router` with
`prerender_config: ""  # no static export; SSR on Vercel`. `resolve_build_dir`
falls back to `./out`, which never exists. Both `wf-acceptance-check` and
`wf-gate-baseline` read the build tree, so **neither can run on this client** —
locally or in CI.

Consequences worth being explicit about:

- lee ships this cycle with **no recorded gate baseline**, so its first PR runs
  the gates bare and inherited debt reads as blocking (sharp edge #1).
- `acceptance_check` — the thing that makes the loop trustworthy, because it
  re-measures rather than believing the model — **did not run**. The 4 claimed
  fixes on this PR are unverified by the gate that exists to verify them.

Needs a decision: give lee a static export target, or set `build_output_dir` to
what Next actually emits and confirm the gates can read a `.next` tree. Until
one of those, this client's loop is open at the end.

**B-010 remains open** and was hit again during onboarding: `preflight` requires
a top-level `industry` that nothing in `pipeline/` ever writes, so the first
`wf-onboard` on any new client stops at exit 11 rather than the documented exit
12 interview step.

## 7. Environment failure that cost a run (not a code bug)

The first remediate attempt on lee returned 10/10 items with
`status: "error"` and this note on each:

```
Claude configuration file not found at: /root/.claude.json
```

`run.sh` mounts `$HOME/.claude-docker` → `/root/.claude`, but Claude Code also
wants `/root/.claude.json`, which lives beside `.claude/` on the host and is not
mounted. With no saved login in `$CLAUDE_HOME` and no `ANTHROPIC_API_KEY`, the
writer never ran.

`run.sh` already warns about this at startup, and `./run.sh claude /login` fixed
it. Recording it because the failure surfaced as **ten per-item errors deep in
`changelog.json`**, not as the startup warning — which is a long way from the
cause, and cost a full cycle to diagnose.

Worth considering: `remediate.py` could check the writer answers once, before
the first item, rather than discovering it ten times.
